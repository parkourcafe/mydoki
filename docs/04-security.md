# 04 · Безопасность — ядро продукта

Здесь хранятся паспорт и свидетельство о рождении ребёнка, медицинские данные.
Утечка = серьёзный вред человеку. Поэтому безопасность — не раздел в конце, а
основа всех решений. Главный контраст с PET ID: там публичный QR — это фича;
**здесь публичности по умолчанию нет**.

## Принципы

1. **Privacy by default.** Ничего не доступно никому, кроме владельца, пока он
   явно не создал ограниченную ссылку.
2. **Least privilege.** Минимум прав у каждого участника и каждого ключа.
3. **Defense in depth.** RLS + приватный storage + signed URL + 2FA — несколько
   независимых барьеров, а не один.
4. **Auditability.** Любой просмотр, скачивание и шеринг логируются.

## Обязательный минимум

- **Приватный storage.** Файлы только через **signed URL с коротким TTL**.
  Никаких публичных ссылок и QR по умолчанию.
- **RLS на каждой таблице.** Доступ скоупится по семье: чтение — любой член
  (`is_household_member`), запись — `editor`/`owner` (`is_household_editor`),
  управление семьёй — `owner`. Авторизация живёт в базе, приложение не может её
  обойти или забыть.
- **2FA / сильная сессия.** Обязательная вторая фаза входа, ограничение по
  устройствам, разумные сроки сессий.
- **Шифрование at-rest.** Supabase шифрует storage. Для топ-чувствительных
  (паспорт, медицина) — рассмотреть **envelope / клиентское шифрование** с
  ключом у пользователя (см. открытые вопросы).
- **Обмен только через explicit share.** Ссылка (`get_shared_document`) ведёт на
  **один** документ; с истечением (`expires_at`), отзывом (`revoked_at`), **лимитом
  просмотров** (`max_views`) и записью каждого доступа в аудит.
- **Полный audit log.** Любой просмотр / скачивание / шеринг фиксируется:
  кто, что, когда, откуда.

## Модель угроз (кратко)

| Угроза | Барьер |
|---|---|
| Чужой пользователь читает мои документы | RLS по владельцу/household на каждой таблице |
| Утёкший signed URL живёт вечно | Короткий TTL; ссылка на 1 файл |
| Расшаренный документ ушёл навсегда | Share: `expires_at` + `revoked_at` + `max_views` + `watermark`, аудит каждого открытия |
| Угон сессии / подбор пароля | 2FA, ограничение устройств, сроки сессий |
| Кража дампа БД | Шифрование at-rest; envelope-шифрование для топ-чувствительных |
| Инсайдер смотрит файлы | Приватный bucket + audit log; минимум сервисных доступов |
| Случайная публикация | Нет публичных путей по умолчанию вообще |

## Доступ по share-ссылке

- Ссылка привязана к **одному** документу, не к профилю человека.
- На каждый доступ проверяются `expires_at`, `revoked_at` и `max_views`.
- `owner`/`editor` может **отозвать** ссылку в любой момент (`revoke_share`).
- Каждое открытие пишется в `audit_log` (`document.share_view`).
- Выдача — через RPC `get_shared_document` (см. [03-architecture.md](03-architecture.md)).
- `watermark` / `allow_download` — флаги водяного знака и разрешения скачивания
  (по умолчанию: водяной знак вкл., скачивание выкл.); RPC отдаёт их клиенту.

## Юридический контур

- Обработка **персональных данных** + **специальной категории (медицина)** →
  явные согласия, политика конфиденциальности, журнал согласий (таблица
  `consents`, enum `consent_kind`: privacy_policy / medical / marketing).
- Осознанный выбор **резидентности данных** (где физически хранится).
- Право на экспорт и удаление всего архива (см. фичи).

## Чек-лист перед публичным запуском

- [ ] RLS включён и покрыт тестами на каждой таблице с данными
- [ ] Bucket приватный; нет ни одного публичного пути к файлам
- [ ] Все ссылки на файлы — signed URL с коротким TTL
- [ ] 2FA обязательна для входа
- [ ] Share проверяет срок, отзыв и лимит просмотров на каждом обращении
- [ ] Audit log пишется через `log_audit` на view / download / share
- [ ] Политика конфиденциальности и согласия (вкл. медицину) готовы
- [ ] Решён вопрос резидентности и шифрования топ-чувствительных данных
- [ ] Бэкапы БД и storage настроены и проверены восстановлением

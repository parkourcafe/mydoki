# 03 · Архитектура

Стек — тот же, что в PET ID, чтобы переиспользовать паттерны и опыт.

```
Next.js (App Router) + Supabase + Vercel
  ├─ Auth: email/пароль или Google OAuth; TOTP-2FA доступна, но НЕ обязательна
  ├─ RSC / route handlers → getSupabaseServer() (общие выборки — в lib/queries)
  ├─ Postgres + RLS — два контура авторизации:
  │    • семейный: household_id + роли owner/editor/viewer
  │    • наём: компания/пользователь через private.can_access_employer()
  ├─ Storage: 5 бакетов — 4 приватных (signed URL) + 1 публичный (портфолио)
  └─ AI (Claude) — авто-распознавание и категоризация документов
```

## Слои

- **Аутентификация.** Supabase Auth: email/пароль либо Google OAuth.
  Двухфакторная защита (TOTP) реализована — выдача фактора в
  `app/my/security/MfaSetup.tsx`, — но **включается по желанию**, а не
  требуется. `app/my/layout.tsx` проверяет наличие подтверждённого фактора и
  показывает мягкую подсказку, причём только когда у пользователя уже есть
  хотя бы один документ: незачем пугать пустой аккаунт. Решение оставить 2FA
  необязательной осознанное: заметная часть входов идёт через Google OAuth,
  где второй фактор обычно уже настроен на стороне аккаунта, так что
  принуждение внутри продукта било бы в основном по тем, у кого защита и так
  есть. Это не «недоделка» — если политика изменится, менять надо и здесь.
- **UI / RSC.** App Router. Кабинет пользователя `/my/*`, кабинет
  работодателя `/employer/*`. Серверные компоненты читают данные на сервере;
  клиент напрямую в Supabase за чужими данными не ходит.
- **Доступ к данным.** Переиспользуемые выборки собраны в `lib/queries.ts`,
  но это не единственная точка входа: страницы и серверные экшены вызывают
  `getSupabaseServer()` напрямую — так делает около полусотни файлов. Для RSC
  это нормальный приём, а не долг: **безопасность держится на RLS, а не на
  слое запросов**, поэтому прямой вызов ничего не ослабляет. Клиентский
  bundle service-ключей не получает.
- **Postgres + RLS.** Авторизация — в базе. Каждая таблица защищена
  политиками RLS; приложение не может «забыть» проверку доступа. Проверки
  вынесены в SECURITY DEFINER-функции схемы `private`
  (`is_household_member` / `is_household_editor` / `is_household_owner`,
  `can_access_employer`, `can_delegate_read_document`), чтобы политики не
  рекурсировали по таблицам, которые сами под RLS.
- **Storage.** Бакетов пять, не один:
  `vault-files` (документы сейфа), `applications` (файлы откликов),
  `employment-docs` (документы по трудоустройству),
  `video-screenings` (видеоответы) — **приватные**, отдаются только через
  `createSignedUrl(s)` с коротким сроком жизни;
  `portfolio-images` — **публичный намеренно**: превью работ фрилансера
  показываются клиенту по публичной ссылке. Публично там только чтение,
  запись ограничена своей папкой `{user_id}/…`, разрешены лишь
  `image/jpeg|png|webp` до 5 МБ (см.
  `supabase/migrations/20260703180000_portfolio_images.sql`). У всех бакетов
  проставлены `file_size_limit` и `allowed_mime_types` — это защита на
  уровне Storage API, помимо клиентской валидации.
- **AI (Claude).** Пайплайн `doc-classify`: по загруженному файлу определить
  тип документа, вытащить номер/даты/кем выдан, предложить категорию.

## Второй контур: наём и трудоустройство

Изначально продукт был только семейным сейфом. Поверх него вырос второй
домен — наём, — и он живёт по другой модели доступа, поэтому описан отдельно.

Сущности: `employer_profiles` (компания) и `company_members` (её сотрудники),
`vacancies` → `applications` (отклик) с сопутствующими
`application_documents` / `application_resumes` / `application_events` /
`application_status_log`, дальше `offers` и `employments` с
`onboarding_tasks` / `offboarding_tasks` / `employment_documents`.

Кто что видит:

- **кандидат** — свои отклики (`applications.user_id = auth.uid()`) и свои
  трудовые записи (`employments.employee_user_id = auth.uid()`);
- **компания** — всё по своим вакансиям и сотрудникам, через
  `private.can_access_employer(company_id)`: это владелец профиля компании
  **или** участник `company_members`;
- **аноним** — только активные вакансии (`status = 'active'`) и портфолио по
  публичному токену.

**Контуры связаны копиями, а не ссылками.** У `application_documents`
собственные `file_path`/`file_name`, внешнего ключа в `documents` нет;
`application_resumes` хранит `sections` как jsonb-снимок. То есть на момент
отклика делается снимок, и он не меняется задним числом: кандидат может
потом отредактировать или удалить оригинал в своём сейфе — работодатель
продолжит видеть ровно то, что ему отправили. Это осознанное свойство, а не
недоделанная нормализация.

## Переиспользуемые паттерны из PET ID

| Паттерн PET ID | Как применяем в Family Vault |
|---|---|
| `document-vault.tsx` | Экран хранилища документов члена семьи |
| Приватный bucket + `createSignedUrls` | Тот же подход, но **без** публичных QR |
| `doc-classify` (AI-классификация) | Авто-определение типа и метаданных при загрузке |
| `reminders` | Напоминания о сроках действия |
| Кабинет `/my/*` | Личный кабинет владельца аккаунта |
| RPC по образцу `get_pet_passport` | **Приватная, истекающая** RPC `get_shared_document` (см. ниже) |

## Важно: отдельный проект, а не модуль PET ID

Другой профиль риска (медицина + удостоверения), другая БД, отдельный домен.
Переиспользуем **код-паттерны и компоненты**, но:

- отдельная база данных,
- отдельные storage-бакеты,
- отдельный домен и деплой,
- отдельный контур согласий и юридических документов.

## RPC выдачи по ссылке

В PET ID `get_pet_passport` отдаёт публичный профиль питомца. В Family Vault
аналог — **`get_shared_document(token)`**, но:

- доступ только по валидному токену (хоть grant и для `anon`),
- проверяет `expires_at`, `revoked_at` и **лимит просмотров** (`max_views` / `view_count`),
- инкрементит счётчик и пишет событие в `audit_log`,
- отдаёт **минимум** (allowlist полей) одного документа + пути файлов, не профиль человека,
- **короткие signed URL** к файлам сервер генерит уже после успешного вызова — bucket остаётся приватным.

Другие RPC: `create_household` (создать семью + сделать создателя `owner`),
`revoke_share` (отозвать ссылку), `log_audit` (единая точка записи аудита).
Хелперы доступа: `is_household_member` / `is_household_editor` / `is_household_owner`.

## Окружения и секреты

- Env-переменные Supabase (URL, anon key, service role) — только на сервере.
- Резидентность данных выбирается осознанно (см. безопасность и открытые вопросы).
- Бэкапы БД и storage — в плане эксплуатации.

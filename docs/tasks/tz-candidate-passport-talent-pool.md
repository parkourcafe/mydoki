# ТЗ: Candidate Passport, Talent Pool и passive recruitment

**Канонический источник:** `docs/DOKI_HELP_ARCHITECTURE_V1_2.md`
**Фазы:** 1B (паспорт), 1C (объяснимое сопоставление), 1E (пул и confidential discovery)
**Статус:** реализовано в этой ветке

---

## 0. Как читать документ

Бриф задачи и канонический документ v1.2 местами используют разные слова для
одних и тех же сущностей. **Источником истины является v1.2.** Термины брифа
поддержаны как синонимы на входе (нормализация), но в коде и БД хранится
каноническое значение.

| Бриф | Канон v1.2 | Где нормализуется |
| --- | --- | --- |
| `candidate_stated` | `candidate_declared` | `normalizeProvenance` |
| `document_extracted` | `extracted_from_candidate_file` | `normalizeProvenance` |
| `employer_verified` | `employer_confirmed` | `normalizeProvenance` |
| `platform_verified` | `externally_verified` | `normalizeProvenance` |
| статус критерия `conflict` | `declared_conflict` | `normalizeCriterionState` |
| статус критерия `stale` | `unknown_stale` | `normalizeCriterionState` |
| `public_to_verified_employers` | `discoverable_pool` | `normalizeVisibilityMode` |
| `confidential` | `confidential_pool` | `normalizeVisibilityMode` |
| membership `joined` | `active` | `normalizeMembershipState` |
| membership `removed` | `left` | `normalizeMembershipState` |
| «приглашение работодателя» | `OpportunityInvite` | — |

Три содержательных расхождения, где выполнен канон, а не бриф:

1. **Фазы.** Бриф относил confidential/blind/snapshot к 1D, а пул — к 1E.
   Канон v1.2 §15: 1B — паспорт, статусы и `ApplicationProfileSnapshot`;
   1C — prefill, нормализация роли и criterion-level explanation; 1D —
   sharing/hardening (bundles, share links); 1E — Talent Pool, видимость,
   блокировки, blind-приглашения. Реализация следует канону.
2. **Employer discovery.** Бриф: «работодатель видит разрешённый уровень
   данных». Канон §8.8.2–3 в первой безопасной версии: работодатель **не
   видит профили вообще** — Doki показывает возможность кандидату, а
   работодателю доступен только агрегат выше порога когорты. Реализовано
   именно так; masked search отложен (§8.8.8).
3. **Приглашение → отклик.** Канон §8.8.6 разделяет `Accept introduction`
   (ограниченный доступ) и `Share & apply` (разрешение + отклик + снимок).
   В брифе это один шаг. Реализованы два события; UI объединяет их в один
   понятный экран, но в аудите они различимы.

## 1. Изменения модели данных

### 1.1. Candidate Passport — расширение `resumes`

v1.2 §7.3 запрещает создавать копию профиля, если существующий можно
безопасно расширить. В репозитории уже есть 1:1-профиль кандидата —
`resumes`. Паспорт добавлен в неё (миграция
`20260819100000_candidate_passport.sql`):

| Группа | Колонки |
| --- | --- |
| Роль | `profession`, `role_taxonomy_code`, `role_free_text`, `seniority`, `years_of_experience` |
| Достижения и команда | `key_achievements`, `management_experience`, `team_size` |
| География | `current_location`, `preferred_locations`, `work_format_preference`, `relocation_willingness` |
| Право на работу | `work_authorization` (`[{country,status,valid_until}]`) |
| Языки | `languages` (`[{code,level}]`, CEFR + `native`) |
| Условия | `salary_expectation` (`{min,max,currency,period}`), `notice_period_days`, `preferred_employment_format` |
| Предпочтения | `preferred_environment`, `motivation`, `company_type_preference`, `role_preference` |
| Вложения | `cv_document_id`, `cv_file_path`, `linkedin_url`, `portfolio_url` |
| Служебное | `search_intent`, `lifecycle`, `field_confirmations`, `last_confirmed_at`, `profile_completeness` |

`field_confirmations` — карта `поле → { source, confirmed_at }`. Источник
хранится по каждому полю, а не по профилю целиком.

`profile_completeness` — свойство **профиля**, не человека: показывается
владельцу и в подсказках «что добавить», для ранжирования людей не
используется (§16).

Старая свободная `resumes.location` сохранена и однократно скопирована в
`current_location`. Свободные `headline / about / experience / custom_fields`
не тронуты — старый экран `/my/resume` продолжает работать.

### 1.2. Новые таблицы (фаза 1B)

| Таблица | Назначение |
| --- | --- |
| `professional_profile_versions` | неизменяемые версии структурированных полей |
| `purpose_authorizations` | purpose-bound разрешения (`talent_pool_discovery` / `opportunity_introduction` / `application`) |
| `application_profile_snapshots` | неизменяемый снимок при отклике: профиль + требования + объяснение + состояние видимости |

Плюс `vacancies.hard_criteria` и `vacancies.soft_signals` — структурированные
критерии роли без весов.

### 1.3. Новые таблицы (фаза 1E)

| Таблица | Назначение |
| --- | --- |
| `talent_pool_memberships` | `not_joined / active / paused / left / expired` + срок |
| `profile_visibility_policies` | 5 режимов видимости, скрытие текущего работодателя, field-level скрытие |
| `organization_discovery_blocks` | блокировка организации или домена |
| `talent_pool_pseudonyms` | псевдоним «кандидат × организация» (`ref`) |
| `opportunity_invites` | blind-приглашения |
| `profile_access_grants` | `introduced` / `shared` доступ с областью и сроком |
| `match_assessments` | оценка пары «версия профиля × версия вакансии» + `valid_until` |
| `profile_access_log` | кто и на каком основании видел профиль |

`employer_profiles` дополнена `domains`, `verification_expires_at`,
`verification_revoked_at` — без действующей верификации discovery невозможен.

### 1.4. Неизменяемость

`professional_profile_versions` и `application_profile_snapshots` защищены
триггером `private.forbid_snapshot_mutation()`: `update` и `delete`
запрещены даже для SECURITY DEFINER-кода. Контрольная сумма (`checksum`)
считается в `lib/passportSnapshot.ts` и позволяет обнаружить подмену.

## 2. Изменения API

### 2.1. Доменные модули (чистая логика, покрыта юнит-тестами)

| Модуль | Ответственность |
| --- | --- |
| `lib/passport.ts` | модель паспорта, происхождение полей, freshness, progressive profiling, prefill |
| `lib/matching.ts` | hard filters / soft signals, состояния критериев, покрытие, `assertNoAggregateScore` |
| `lib/talentPool.ts` | членство, `PurposeAuthorization`, когортный порог, приглашения, `assertNoInviteHistorySignal` |
| `lib/passportVisibility.ts` | режимы видимости, `discoveryDecision`, проекция профиля, `assertNoIdentityLeak` |
| `lib/passportSnapshot.ts` | версия профиля, снимок отклика, детерминированная сериализация и checksum |

### 2.2. RPC (SECURITY DEFINER)

**Кандидат:**

| Функция | Что делает |
| --- | --- |
| `set_search_intent(text)` | `active / open / unavailable` |
| `publish_profile_version(jsonb, text)` | фиксирует неизменяемую версию профиля |
| `grant_purpose_authorization(...)` | разрешение с целью, основанием, областью и сроком |
| `revoke_purpose_authorization(text)` | прекращает новые показы, снимки не переписывает |
| `set_profile_visibility(...)` | режим, скрытие работодателя, field-level скрытие |
| `set_talent_pool_membership(state, expires_at)` | вступление/пауза/выход; `active` требует действующего разрешения |
| `block_organization(uuid, text)` / `unblock_organization(uuid)` | блокировка организации/домена; отзывает выданный доступ и приглашения |
| `get_my_opportunity_invites()` | приглашения кандидата вместе с объяснением |
| `respond_to_opportunity_invite(id, action, scope)` | `view` / `accept` / `decline` |
| `share_and_apply(...)` | разрешение + `Application` + неизменяемый снимок |
| `record_application_profile_snapshot(...)` | снимок для обычного отклика (в т.ч. по секретному токену) |

**Работодатель:**

| Функция | Что делает |
| --- | --- |
| `talent_pool_candidates(limit)` | анонимные строки пула: `ref`, поля критериев, `reveal_level`; без имени, контактов, CV, ссылок и свободного текста |
| `send_opportunity_invite(...)` | blind-приглашение по `ref`; проверяет верификацию, блокировки, полноту раскрытия и лимит 25/сутки |
| `get_employer_invites()` | свои приглашения; профиль появляется только после принятого знакомства |

Все выдачи работодателю проходят `private.discovery_denied_reason()` —
серверный аналог `discoveryDecision()` из TS.

### 2.3. Server actions

- `app/my/passport/actions.ts` — сохранение паспорта, статус, версия
  профиля, подтверждение актуальности, приём prefill, видимость, пул, блоки.
- `app/my/opportunities/actions.ts` — просмотр, принятие знакомства, отказ,
  `Share & apply` (собирает объяснение и снимок на сервере).
- `app/employer/talent/actions.ts` — `previewCohort` (только агрегат),
  `sendBlindInvites` (оценка критериев на сервере Doki, рассылка по `ref`).

## 3. UI-потоки

### 3.1. Онбординг кандидата (`/my/passport`)

1. **Шаг 1 — минимальный профиль (7 полей, ориентир 60–90 секунд):**
   профессия (или свободное описание роли), текущая локация, уровень, языки,
   зарплатные ожидания, статус поиска, формат работы. Длинной анкеты на
   первом экране нет.
2. **Шаг 2 — progressive profiling:** право на работу, готовность к
   переезду, notice period, опыт, управленческий опыт и размер команды,
   достижения, мотивация, среда, CV и ссылки. Подсказка «что добавить
   дальше» сначала предлагает поля, улучшающие объяснимость обязательных
   критериев.
3. **Версия профиля:** кнопка «зафиксировать версию» создаёт неизменяемый
   снимок, на который ссылаются отклик и оценка.
4. **Видимость и Talent Pool:** режим видимости (по умолчанию `private`),
   скрытие текущего работодателя, скрытие отдельных полей, вступление в пул
   с отдельным текстом разрешения и сроком, блокировки организаций.
   При рискованном сочетании полей показывается предупреждение о косвенной
   идентификации — обещания полной анонимности нет.

CV можно приложить, но интерфейс прямо говорит: сопоставление строится по
структурированным полям, которые кандидат подтвердил.

### 3.2. Возможности кандидата (`/my/opportunities`)

Приглашение показывает организацию (с отметкой верификации), роль, локацию,
формат, диапазон компенсации, **цель доступа к данным** и срок ответа —
иначе оно не может быть отправлено. Раскрывается блок «почему вам показали
эту роль» с criterion-by-criterion объяснением.

Действия: `Принять знакомство` → ограниченный доступ (ещё не отклик);
`Отклонить` (с явной пометкой, что отказ не влияет на будущие подборки);
после принятия — выбор передаваемых полей и `Передать данные и откликнуться`.

### 3.3. Employer matching view (`/employer/talent`)

Доступен только организации с действующей верификацией.

1. Выбор вакансии; если структурированных критериев нет — предупреждение,
   сопоставлять нечего.
2. `Показать размер когорты` — единственный агрегат: корзина `10–15`, а ниже
   порога (5) результат подавляется целиком.
3. Кампания: роль, локация, формат, компенсация, цель доступа, срок ответа,
   сообщение → `Отправить обезличенные приглашения`. Ниже порога когорты
   кампания не запускается.
4. Список приглашений: состояние; после принятого знакомства — разрешённые
   поля профиля и блок «покрытие требований» с состояниями по каждому
   критерию. Процента совпадения и сортировки людей нет нигде.

## 4. Правила доступа и видимости

Порядок проверок (одинаков в `lib/passportVisibility.ts::discoveryDecision`
и в `private.discovery_denied_reason`):

1. организация заблокирована кандидатом (по id или домену) → **none**;
2. организация — текущий работодатель (по названию или домену) → **none**;
3. верификация организации отсутствует, отозвана или истекла → **none**;
4. режим видимости `private` → **none**;
5. `search_intent = unavailable` → **none**;
6. членство в пуле не `active` или истекло → **none**;
7. нет действующего разрешения `talent_pool_discovery` → **none**;
8. есть `ProfileAccessGrant` → **introduced**;
9. `invited_only` → **none**; `recommendations_only` → только кандидату;
10. `confidential_pool` → **blind**; `discoverable_pool` → **pool_fields**.

Уровни раскрытия:

| Уровень | Что видит работодатель |
| --- | --- |
| `none` | ничего |
| `recommendation_only` | ничего (возможность видит только кандидат) |
| `blind` | поля обязательных критериев; без имени, контактов, CV, ссылок, текущего работодателя и свободного текста |
| `pool_fields` | то же + управленческий опыт, размер команды, тип компании |
| `introduced` | + свободный текст в объёме гранта |
| `shared` | поля и контакты, которые кандидат явно передал для этой цели |

Границу «личность не раскрывается» держит БД: `talent_pool_candidates` и
`get_employer_invites` физически не возвращают имя, контакты, CV, ссылки и
`user_id`; работодатель оперирует псевдонимом `ref`. Прямого SELECT на
`opportunity_invites` у работодателя нет (иначе `user_id` кандидата утёк бы
через PostgREST до принятия знакомства) — только RPC.

Field-level скрытие применяется в SQL: `talent_pool_candidates` вычитает
`hidden_fields` из выдачи пула, `private.invite_profile()` — из профиля по
принятому знакомству, и там же применяется `scope_fields` гранта. Снимок
обычного отклика тоже собирается без скрытых кандидатом полей.

Guardrails в коде: `assertNoIdentityLeak`, `assertNoAggregateScore`,
`assertNoInviteHistorySignal`.

## 5. Заметки по миграции

Обе миграции аддитивны, идемпотентны (`if not exists` / `duplicate_object`)
и содержат план отката в шапке файла.

1. `20260819100000_candidate_passport.sql`
   - расширяет `resumes`, добавляет 3 таблицы, 2 колонки вакансии, 5 RPC;
   - бэкофилл: `current_location := location` там, где пусто;
   - существующие строки `resumes` получают `search_intent = 'open'`,
     `lifecycle = 'draft'` → профиль остаётся черновиком и не обнаруживается,
     пока человек сам не заполнит минимальный набор;
   - обратная совместимость: `/my/resume`, отклики и Doki.id не затронуты.
2. `20260819110000_talent_pool_confidential_discovery.sql`
   - 8 таблиц, 3 приватных хелпера, 9 RPC, колонки верификации организации;
   - **важно:** после применения ни один существующий профиль не попадает в
     пул: нужны явные `set_profile_visibility` + разрешение + членство;
   - уже верифицированные работодатели сохраняют верификацию
     (`verification_expires_at` пуст = бессрочна до отзыва).

Порядок применения — по именам файлов. Откат: выполнить блок из шапки файла
в обратном порядке (сначала 1E, затем 1B).

Проверка: полная цепочка миграций (включая обе новые) применена локально на
PostgreSQL 16 без ошибок, SQL-тесты из `tests/rls/` прошли с ожидаемыми
значениями. Против живой базы Supabase миграции в этой ветке не выполнялись —
`supabase db push` на staging обязателен перед релизом.

## 6. Тест-кейсы

### 6.1. Юнит (`npm run test:unit`, 53 новые проверки: 10 + 17 + 18 + 8)

`tests/unit/passport.test.ts`
- минимальный профиль создаётся без вакансии и без CV;
- первый шаг — ровно 7 полей;
- `Other role` заменяет профессию;
- `active/open/unavailable`, `unavailable` останавливает новые предложения;
- полнота растёт и подсказывает следующий шаг;
- синонимы источников приводятся к канону; заявленное ≠ verified;
- устаревшее поле помечается, а не превращается в несоответствие;
- непринятая prefill-подсказка не попадает в профиль;
- источник, не предоставленный кандидатом, к prefill не допускается.

`tests/unit/matching.test.ts`
- в выводе нет `score`, `percent`, `rank`, `weight`; guardrail срабатывает;
- покрытие считается по критериям (`8 met, 1 needs_verification`);
- канонический пример §8.7 «семь из восьми»;
- нет данных → `unknown`, устарело → `unknown_stale`, заявленное
  несовпадение → `declared_conflict` (и только оно исключает из выдачи);
- несравнимая валюта не выдумывает курс;
- право на работу требует проверки; национальность как proxy не участвует;
- удалённая роль снимает географию; `conditional` — вопрос, а не отказ;
- soft signals не создают конфликт;
- наличие CV не меняет результат сопоставления;
- оценка привязана к паре версий и имеет срок;
- порядок показа детерминирован и не зависит от «качества».

`tests/unit/passportVisibility.test.ts`
- дефолт `private`; синонимы режимов нормализуются;
- неподтверждённая организация, блокировка (id и домен), текущий
  работодатель, `unavailable`, неактивное членство, отозванное разрешение —
  каждый случай закрывает discovery;
- истёкшее членство → `expired`, профиль сохраняется;
- confidential → `blind`: в выдаче нет имени, контактов, CV, ссылок,
  достижений и мотивации;
- `recommendations_only` не даёт работодателю ничего;
- double opt-in: личность только на уровне `shared`, и только переданные поля;
- field-level скрытие; guardrail ловит утечку личности;
- предупреждение о косвенной идентификации;
- когорта ниже порога подавляется, выше — округляется;
- приглашение без раскрытия условий и цели не отправляется;
- отказ не становится свойством профиля.

`tests/unit/passportSnapshot.test.ts`
- снимок содержит четыре части и метку времени;
- правка паспорта после отклика не переписывает снимок;
- контрольная сумма ловит подмену;
- сериализация детерминирована;
- в снимок попадают только переданные поля;
- совокупный балл и скрытые веса в снимок не проходят;
- история реакций на приглашения в профиль не попадает.

### 6.2. RLS/SQL (`tests/rls/`)

`talent_pool_visibility.sql` — транзакция с откатом проверяет: работодатель
не читает `resumes`; приватный профиль не обнаруживается; confidential
отдаётся без идентификаторов и без `user_id`; блокировка и текущий
работодатель закрывают выдачу; `unavailable` останавливает показы, членство
сохраняется; организация без действующей верификации получает исключение;
отзыв разрешения прекращает показы; снимок нельзя изменить или удалить.

`opportunity_invite_flow.sql` — сценарий blind-приглашения: приглашение без
раскрытия условий и цели не отправляется; отправка идёт по псевдониму `ref`;
до принятия знакомства `profile = null` и в ответе нет ни `user_id`, ни
имени, ни контактов; после принятия видны только разрешённые поля;
`Share & apply` создаёт один отклик, одно разрешение и один снимок, а
повторный вызов ничего не переписывает.

Обе миграции и оба SQL-теста прогонялись локально на PostgreSQL 16 с
минимальной имитацией Supabase-окружения (схемы `auth`/`storage`, `auth.uid()`,
роли `anon`/`authenticated`): полная цепочка миграций применяется без ошибок,
все ожидаемые значения совпали. Прогон против staging Supabase остаётся
обязательным перед релизом.

## 8. Что осознанно не сделано

- **Masked employer search** — по §8.8.8 появляется только после проверки
  blind-модели; сейчас работодатель не получает построчную выдачу.
- **AI-нормализация роли в taxonomy** (фаза 1C) — поле
  `role_taxonomy_code` и его подтверждение кандидатом готовы, сам
  нормализатор подключается отдельной задачей к существующему AI-слою.
- **Автоматическое извлечение из CV** — механика review/confirm реализована
  (`acceptPrefill`), источник извлечения подключается отдельно; скрытый
  scraping закрытых профилей не реализуется никогда (§16).
- **Cron переподтверждения устаревших профилей** — правила freshness и
  `fieldsNeedingReconfirmation` готовы, регулярная рассылка не добавлена.
- **Остаточный риск differencing:** кампания не запускается ниже порога
  когорты, действует лимит 25 приглашений в сутки и лимит поисков в час, но
  сравнение двух кампаний с разными критериями всё ещё даёт работодателю
  косвенную информацию. Полное решение (шум/бюджет запросов) — отдельная
  задача.

## 9. Решения владельца (зафиксировано перед merge)

1. **Anonymous match explanation.** `record_application_profile_snapshot()`
   вызывается в том числе анонимно (обычный отклик без аккаунта), поэтому
   `match_explanation_snapshot` на этом пути приходит от вызывающей стороны и
   доверенным выводом Doki не является. **Решение:** показывать это объяснение
   работодателю запрещено до тех пор, пока Candidate Card не будет
   пересчитывать его на сервере из неизменяемого снимка профиля и версии
   вакансии. Сейчас ни один экран его не отображает — ограничение действует
   на будущую реализацию Candidate Card.
2. **Differencing между кампаниями.** Порог когорты (5), округление до
   корзины, лимит 25 приглашений в сутки, лимит 600 поисков в час и
   `profile_access_log` внедрены, но сравнение двух кампаний с разными
   критериями всё ещё даёт работодателю косвенную информацию об аудитории.
   **Решение:** принимается как residual risk **только для MVP**; полноценная
   защита (шум или бюджет запросов) — отдельная задача до масштабирования
   Talent Pool.
3. **Perf-budget.** Провал `apply/[slug]: 191.2 KB > 150 KB` воспроизводится
   на базовой ветке без этих изменений и к PR отношения не имеет.
   **Решение:** если branch protection требует зелёный CI, merge блокируется
   до отдельного фикса веса `apply/[slug]` или до явного пересмотра лимита в
   `perf/check-bundle.mjs`. Обходить проверку в рамках этого PR не следует.

## 10. Staging gate (результат прогона)

Прогон выполнен на локальном стеке «staging-like Supabase»: PostgreSQL 16 +
PostgREST 12.2.3 + шим `/auth/v1/user`, полная цепочка из 63 миграций.

- миграции применяются без ошибок, включая обе новые;
- оба SQL-теста из `tests/rls/` зелёные;
- 13/13 проверок через REST/PostgREST (см. §11);
- 15/15 smoke-проверок четырёх маршрутов;
- обычный отклик, отправленный через реальный UI, создал `applications` и
  `application_profile_snapshots` с контрольной суммой.

Против настоящего Supabase-проекта миграции **не** применялись: staging-проекта
в организации нет (есть только продовый `mydoki`), а создание Supabase-branch —
платное действие, требующее решения владельца.

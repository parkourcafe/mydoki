# ТЗ фазы 2 — Employment (оффер, оформление, трудовые отношения)

*Task-документ по Архитектуре v1.1 (`docs/ARCHITECTURE.md` §7.4, §14, §16) и аудиту (`docs/CODE_AUDIT.md`). Дата: 12.07.2026. Фаза 1 завершена (PR-0…14).*

## 0. Границы и принципы фазы 2

**Ключевая сущность — `Employment` (v1.1 §7.4):** ОДНА каноническая запись о трудовых отношениях с ДВУМЯ интерфейсными проекциями:
1. карточка сотрудника у работодателя (`/employer/employees/[id]`);
2. «Мои трудовые отношения» у человека (`/my/employment`).

Это НЕ две копии данных (v1.1 §15 запрещает две независимые сущности). Точка создания — `application.state='hired'` (задел фазы 1 уже есть).

**Ручной режим (v1.1 §7.4, аудит-перспектива §3.1):** человек добавляет свою трудовую историю сам, даже если работодатель не в Doki (иначе раздел пуст у 95% пользователей). Обязательно с самого начала.

**Входит в фазу 2:** Employment (обе проекции + ручной режим); оффер (генерация + подтверждение согласием, e-signature — интеграцией, не своей криптографией); оформление (комплект документов); онбординг (чек-листы, точки 7/30/60/90); напоминания работодателя (визы/договоры/сертификации).

**Не входит (фаза 3+):** изменения условий/допсоглашения/повышения (фаза 3), юрпомощник (фаза 3), увольнение как процесс/архив/внешняя верификация (фаза 4).

**Рамки (как в фазе 1):** аддитивные миграции (общая БД с Doki.id), RLS — граница доступа, 4 локали, проверка на локальном Postgres, без вердиктов/баллов, человек принимает решения.

## 2. P2-1 — модель

`employments` (аддитивно):
- `id`, `company_id` (→ employer_profiles.id, NULLABLE — ручной режим), `company_name` (денормализация/ручной режим),
- `employee_user_id` (→ auth.users, человек), `application_id` (→ applications, NULLABLE — источник hired или null),
- `position`, `employment_type` (`full_time|part_time|contract|intern|other`), `start_date`, `end_date` (nullable),
- `status` (`active|ended`), `manual` (boolean — добавлено человеком vs из hired),
- `created_by`, `created_at`, `updated_at`.

RLS: чтение — `employee_user_id = auth.uid()` ИЛИ `private.can_access_employer(company_id)` (владелец/рекрутёр компании). Запись: человек управляет своими ручными (`manual=true and employee_user_id=auth.uid()`); работодатель управляет записями своей компании (`can_access_employer(company_id)`). Employment из hired — через SECURITY DEFINER RPC (проверяет владение вакансией + state='hired').

`create_employment_from_application(p_application_id, p_position, p_type, p_start_date)`: проверяет, что вызывающий владеет вакансией и отклик hired; создаёт employment (company_id = employer, employee_user_id = application.user_id, application_id, manual=false); идемпотентно (не дублирует для того же application_id).

## 3. P2-1 — экраны (4 локали)

- **`/my/employment`** — «Мои трудовые отношения»: список (компания, должность, период, статус, метка «ручная»/«от работодателя»); форма «Добавить место работы» (ручной режим: компания-текст, должность, тип, даты); деталь `/my/employment/[id]`.
- **`/employer/employees`** — список сотрудников компании (из employments); карточка `/employer/employees/[id]` (должность, тип, период, источник-отклик, статус; правка).
- **Candidate Card:** при `state='hired'` — кнопка «Оформить сотрудника» → `create_employment_from_application` → переход в карточку сотрудника.
- Ссылки в навигации: `/my/work` (карьерный хаб) → «Мои трудовые отношения»; шапка работодателя → «Сотрудники».

## 4. P2-1 — приёмка

Работодатель на hired-отклике создаёт Employment → он виден и в `/employer/employees`, и у человека в `/my/employment` (одна запись, две проекции). Человек добавляет ручное место работы (без работодателя в Doki) → видно только у него. RLS: чужой не видит; рекрутёр компании видит сотрудников. typecheck/build/локальный Postgres зелёные. Employment из hired идемпотентен.

# ТЗ фазы 3 — Трудовые отношения (изменения условий) + юридический помощник

*Task-документ по Архитектуре v1.1 (`docs/ARCHITECTURE.md` §7.4, §11.3, §13, §14 «Фаза 3»). Дата: 13.07.2026. Фаза 2 завершена (P2-1…P2-4).*

## 0. Границы и принципы фазы 3

**Что входит (арх. §14 «Фаза 3»):** изменения условий трудовых отношений; допсоглашения; повышения; переводы; напоминания работодателя о пересмотрах; юридический помощник — **одна юрисдикция**, Process Guide, курируемая база (§13).

**Ключевой принцип изменений (§7.4):** Employment — ОДНА каноническая запись. Изменение условий — это допсоглашение (amendment): предложение работодателя, **подтверждённое согласием человека** (как оффер в фазе 2), после чего применяется к текущим условиям employment. История изменений неизменяема.

**Юридический слой (§13):** Doki.help НЕ даёт универсальных юридических заключений. Только: одна юрисдикция за запуск; курируемая база; версия источника + дата обновления; явный дисклеймер; маршрут к специалисту. Process Guide (§11.3) — контекстные информационные подсказки, без вердиктов, без автодействий.

**Рамки (как в фазах 1–2):** аддитивные миграции (общая БД с Doki.id), RLS — граница доступа, записи с состояниями — только через SECURITY DEFINER RPC, 4 локали, проверка на локальном Postgres, без вердиктов/баллов, человек принимает решения.

**Не входит (фаза 4):** оффбординг/увольнение, расчёт, возврат имущества, архив, внешняя верификация, семья.

## 2. P3-1 — модель

`employments` (аддитивно): `compensation text` — текущая оплата (обновляется принятыми повышениями/изменениями оплаты).

`employment_amendments`:
- `id`, `employment_id` (→ employments),
- `kind` (`promotion|transfer|comp_change|schedule_change|terms_change|other`),
- `effective_date` (date — с какой даты вступает),
- `new_position`, `new_employment_type`, `new_compensation` (nullable — что меняется),
- `terms` (nullable — описание изменения/условия), `note`,
- `disclaimer` (юр-статус: допсоглашение имеет силу при подписании; не электронная подпись),
- `status` (`draft|proposed|accepted|declined|withdrawn`),
- `created_by`, `created_at`, `proposed_at`, `responded_at`, `responded_actor`, `updated_at`.

RLS: чтение — через видимость employment (сотрудник видит свои, компания — свои). Запись — только через SECURITY DEFINER RPC (как offers: прямые insert/update/delete запрещены). Может быть несколько амендментов на employment (в отличие от одного оффера).

RPC:
- `upsert_employment_amendment(...)` — работодатель создаёт/правит черновик (гейт `can_access_employer`);
- `propose_employment_amendment(p_id)` — перевод в `proposed` (виден сотруднику);
- `withdraw_employment_amendment(p_id)` — отзыв;
- `respond_to_amendment(p_id, p_accept, p_consent)` — **сотрудник (authenticated, `employee_user_id = auth.uid()`)**: accept требует согласия, фиксирует дисклеймер/время/actor и **применяет** новые значения к `employments` (должность/тип/оплата/окончание); деклайн — без изменений.

## 3. P3-1 — экраны (4 локали)

- **`/employer/employees/[id]`** — секция «Изменения условий»: форма допсоглашения (вид, дата вступления, новые должность/тип/оплата, условия, заметка), «Предложить»/«Отозвать»; список истории со статусами.
- **`/my/employment/[id]`** — ожидающее допсоглашение (`proposed`): детали + дисклеймер + чекбокс согласия + «Принять»/«Отклонить» (`respond_to_amendment`); история принятых изменений.

## 4. P3-1 — приёмка

Работодатель предлагает повышение (новая должность+оплата, дата вступления) → человек видит у себя, принимает с согласием → employment обновляет должность/оплату, амендмент фиксируется в истории с дисклеймером/временем. Деклайн — условия не меняются. RLS: чужой не видит/не трогает; запись только через RPC. typecheck/build/локальный Postgres зелёные.

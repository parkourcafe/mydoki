# Автономный бэклог doki.help (Индонезия)

> Этот файл — источник правды для работы в режиме `/loop` без участия владельца.
> Агент берёт **первую незакрытую** задачу сверху, доводит её до критериев
> приёмки, проходит гейт проверки, отмечает `[x]`, коммитит и переходит к
> следующей. Если задача блокируется — помечает `[!]` с причиной и идёт дальше,
> НЕ останавливая цикл.

## Правила цикла

1. **Одна задача за итерацию.** Не браться за следующую, пока текущая не закрыта
   или не помечена `[!]`.
2. **Гейт проверки — обязателен для каждой задачи** (см. ниже). Задача не
   считается закрытой, пока гейт не зелёный.
3. **Один коммит на задачу**, сообщение описывает эффект для пользователя.
   Пушить в `claude/new-session-t23vhc` после каждой задачи.
4. **PR** — один на группу задач (см. группы), не на каждую задачу.
5. **Ветка**: перед началом новой группы — `git fetch origin claude/cool-volta-pdpl4t`
   и `git checkout -B claude/new-session-t23vhc origin/claude/cool-volta-pdpl4t`,
   если предыдущий PR смержен. Если нет — продолжать в текущей ветке.
6. **Отмечать прогресс прямо в этом файле** (`[ ]` → `[x]` / `[!]`) и включать
   правку файла в тот же коммит.
7. **Остановиться** только когда все задачи `[x]` или `[!]`, и написать итог.

### Гейт проверки (каждая задача)

```
npx tsc --noEmit        # без ошибок
npm run test:lexicon    # OK
npm run test:unit       # 96/96 или больше, без падений
npm run build           # успешно
```
Если гейт красный — чинить в той же итерации, не переходить дальше. Если после
трёх попыток не чинится — `[!]` с описанием, что именно не сходится.

## Заранее принятые решения (не спрашивать владельца)

Это ответы на вопросы, которые иначе остановили бы цикл:

| Вопрос | Решение |
|---|---|

| Лимит вакансий при закрытии | Закрывать разрешаем свободно. Лимит остаётся по активным. Антиабьюз — потом, по факту, а не превентивно. |
| Модель статусов кандидата | Главная — **доска** (`new/viewed/shortlisted/rejected/hired`). Карточка получает те же действия, стадии остаются как доп. измерение. Большой рефактор не делаем. |
| Осиротевшие файлы с русским | **Удалить** (`lib/roleTemplates.ts`, `lib/vacancyWizard.ts`, `RolePicker.tsx`, `WizardIntake.tsx`, `ShareBox.tsx`). Они без импортёров и содержат только русский. |
| Язык новых строк | Все 4 локали обязательны. Индонезийский — первым по важности, дефолт при неизвестной локали — `id`. |
| Спорная формулировка в копирайте | Выбирать более осторожную. Ничего не обещать сверх того, что подтверждается кодом. |

## Группа 3 — найм без аккаунта у кандидата (главный тупик)

**Итог:** реализован вариант **A**. Работодатель шлёт принятому кандидату
приглашение в WhatsApp; кандидат заводит аккаунт и сам привязывает отклик со
своей страницы статуса, после чего `applications.user_id` заполняется и
оформление сотрудника становится доступным.

✅ **Уязвимость в `claim_application` закрыта** (`20260802120000_...`).
Исходная функция проверяла только факт аутентификации: любой залогиненный с
`access_token` привязывал чужой отклик к себе, а `claimApplication` копировал
документы кандидата (KTP, справки) в его сейф. **Воспроизведено на живой БД**
до починки: `application_belongs_to` становился id атакующего.

Теперь требуется совпадение личности — email аккаунта с `applications.email`
либо телефон с `applications.whatsapp` (сравниваются только цифры, хвост 8
знаков: индонезийские номера пишут и как `0812…`, и как `62812…`). Отказ
возвращает причину, и страница привязки объясняет её кандидату.

**Прогон выполнен реально**, не на бумаге: поднят локальный Postgres 16,
применены миграции с Supabase-заглушками, прогнаны все 4 набора RLS-тестов.
Результаты совпали с ожидаемыми: `claim_application` 8/8, `isolation` 1|1|0|0,
`document_versions` 1|0|0|0|0, `invitations` 0|2|editor. Инструкция по
воспроизведению — `tests/rls/README.md`, заглушки — `tests/rls/_local_shim.sql`.

⚠️ Заглушки лишь приближают Supabase. Зелёный локальный прогон не заменяет
проверку на реальном проекте при изменении политик.

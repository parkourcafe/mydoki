# Reactive Resume → что из этого стоит взять в doki.help

Разбор кода `github.com/AmruthPillai/Reactive-Resume` (клон от 2026-08-23,
лицензия **MIT**) с точки зрения нашего продукта: `app/my/resume`,
`app/apply/[slug]`, `app/employer/candidates`, `app/portfolio/[token]`.

---

## Статус реализации

- **Волна 1 — сделано.** `resumes.sections` (структурный опыт, обучение, навыки,
  языки), `lib/resume.ts`, детерминированная проверка `lib/resumeQuality.ts`,
  редактор секций и полоса готовности на `/my/resume`, снимок резюме в отклике
  (`application_resumes`) и блок «Резюме кандидата» в карточке у работодателя.
  Миграции применены к проекту `mydoki`.
- **Волна 2 — сделано.** Серверный PDF через `@react-pdf/renderer` без headless-браузера:
  `lib/pdf/` (шрифт Roboto из репозитория ради кириллицы, общая типографика,
  документы CV и справки о работе). Маршруты: `/my/resume/pdf` (своё CV),
  `/employer/candidates/<id>/resume-pdf` (копия из снимка отклика),
  `/employer/employees/<id>/letter` и `/my/employment/<id>/letter` (справка о
  работе; личная ссылка-подтверждение попадает только в копию самого работника —
  читать её по RLS может лишь он).
- **Проверяемый опыт — сделано.** Строка резюме может ссылаться на запись
  `employments`: «＋ В резюме» на `/my/career`, отметка «подтверждено» для записей,
  оформленных работодателем (`manual = false`), в форме, в карточке кандидата у
  работодателя и в CV-PDF. Отметку ставит только сервер (`lib/resumeLinks.ts`) —
  в `resumes.sections` она не хранится, поэтому приписать её себе нельзя.

- **Волна 3 — сделано.** Импорт старого CV файлом через существующий контур ИИ
  (`/api/resume-parse`, версионируемый промпт `resume_import`, разбор и слияние —
  чистые функции в `lib/resumeImport.ts`) и открытый формат JSON Resume в обе
  стороны (`lib/jsonResume.ts`, выгрузка `/my/resume/json`, загрузка прямо в
  браузере). Импорт ничего не затирает: пустые поля заполняет, записи добавляет
  только новые.

---

## TL;DR

1. **Их главная ценность для нас — не «конструктор резюме», а четыре
   инженерных куска**: структурная модель резюме, серверный экспорт в PDF без
   headless-браузера, детерминированный ATS-линтер и промпт-парсер «старое CV →
   структурный JSON».
2. **Наше резюме сейчас — плоский текст** (`resumes.experience text`,
   `supabase/migrations/20260703140000_resumes.sql`), и работодателю оно вообще
   не показывается: в `app/apply/[slug]/page.tsx:150` из него берут только
   `full_name / contact / email` для предзаполнения формы. Это самая дешёвая
   недоиспользованная сущность в продукте.
3. **PDF через `@react-pdf/renderer`** (их `packages/pdf/src/server.tsx`)
   работает в serverless — нам это открывает не только CV кандидата, но и
   генерацию кадровых бумаг (справка о работе, оффер, финальные документы),
   где у нас уже есть данные, но нет выдачи файла.
4. **Мы можем сделать то, чего Reactive Resume сделать не может: проверяемое
   резюме.** У нас есть `employments` (с флагом `manual` — «из найма» vs «руками»)
   и `employment_verifications`. Строка опыта, подтверждённая работодателем
   внутри doki, — это дифференциатор, а не ещё один шаблон CV.
5. **Чего брать не надо:** движок шаблонов, style-rules, drag-n-drop layout,
   свою типографику и шрифты. Это половина их кодовой базы и она решает задачу
   не нашей аудитории.

## Где мы пересекаемся и где мы сильнее

| | Reactive Resume | doki.help |
|---|---|---|
| Центр модели | документ «резюме» (много версий, много шаблонов) | человек + его **настоящие** документы в сейфе |
| Опыт работы | самодекларация | `employments` из реального найма + верификация работодателем |
| Публикация | публичная ссылка/слаг, индексируемая | share с TTL, отзывом, лимитом просмотров и аудитом (`app/s/[token]`, `revoke_share`) |
| Работодатель | отсутствует как роль | полноценный контур: вакансии, отклики, стадии, наём, кадровые документы |
| Локаль/рынок | глобальный, EN-first | ID/RU/EN/UZ, Индонезия, часто «синие воротнички» и экспаты |

Вывод: мы **не конкурируем** с ними. Мы можем взять их инженерные решения и
поставить их на нашу уникальную базу данных (подтверждённый трудовой опыт +
документы в сейфе).

## Что стоит взять

### 1. Структурная модель резюме вместо плоского текста

**У них:** `packages/schema/src/resume/data.ts` — zod-схема: `basics`
(имя, email, телефон, локация, сайт, customFields) + типизированные секции
`experience / education / skills / languages / projects / certifications /
awards / volunteer / publications / references / profiles / interests`, каждая
запись с `id`, `hidden`, периодом и описанием в HTML.

**У нас:** одна строка на пользователя, `experience` — один `text`
(`app/my/resume/ResumeForm.tsx`).

**Что делать:** не копировать всю схему (у них ~700 строк вместе со стилями), а
взять подмножество: `basics` + `experience[]` + `education[]` + `skills[]` +
`languages[]` + существующие `custom_fields`. Хранить как `jsonb` в `resumes`,
аддитивной миграцией, со старым `experience text` как fallback.

**Зачем:** без структуры невозможны ни PDF, ни проверки качества, ни
сопоставление с вакансией, ни автозаполнение отклика. Это фундамент для пунктов
2–5.

**Оценка:** ~1 день (миграция + форма-редактор секций + чтение старого формата).

---

### 2. Экспорт в PDF без headless-браузера

**У них:** `packages/pdf/src/server.tsx` — `renderToBuffer(<ResumeDocument/>)`
на `@react-pdf/renderer`, возвращает `File`. Никакого Puppeteer/Chromium.

**Почему это важно именно нам:** у нас Vercel и Capacitor-обёртка; headless
Chrome там дорог и хрупок. `@react-pdf/renderer` — обычная npm-зависимость,
рендерится в Node-рантайме серверного экшена.

**Что это даёт, кроме CV:**
- **CV-однострочник кандидата** — прикладывается к отклику и ложится в сейф как
  обычный документ (значит, автоматически получает наш share с TTL и аудитом).
- **Кадровые бумаги работодателя.** У нас уже есть данные в `employments`,
  `offers`, `employment_verifications`, `final_documents` — но выдачи файла нет.
  Справка о работе / оффер в PDF — это то, за что в Индонезии реально платят.
- **Экспорт архива** (`app/my/export`) — сводка по человеку одним файлом.

**Оценка:** ~1 день на инфраструктуру + 0.5 дня на каждый шаблон документа.
DOCX (их `packages/docx`, библиотека `docx`) — по тому же принципу, если
понадобится.

---

### 3. ATS-линтер: детерминированные правила вместо «спросим ИИ»

**У них:** `packages/resume/src/ats/` — 22 правила в каталоге
(`catalog.ts`), каждое с `severity` (`error|warning|info`), человеческим
объяснением `meaning` и конкретным действием `action`. Находки
(`AtsFinding`) адресуются JSON-указателем (`/basics/email`), отчёт считает
`passedRules / totalRules`. Ноль вызовов LLM.

**У нас ровно тот же паттерн уже есть** — `lib/vacancyQuality.ts` (проверка
качества вакансии, `clarityScore`, `warnings`) и `lib/ai/completeness.ts`
(комплектность документов отклика). То есть архитектурно мы уже согласны с их
подходом; не хватает третьей стороны — **качества профиля кандидата**.

**Что делать:** `lib/resumeQuality.ts` по образцу `vacancyQuality.ts`: нет
контакта, нет ни одной записи опыта, период задом наперёд, дата в будущем,
описание роли пустое, ссылка без протокола. Правила — свои, наши: под ID-рынок
важнее «нет WhatsApp» и «нет разрешения на работу», чем «в CV есть фото».

**Зачем:** бесплатно (без токенов), мгновенно, работает офлайн, объяснимо
пользователю и даёт честную метрику полноты профиля для аналитики.

**Оценка:** ~0.5 дня, тесты — в существующем стиле `tests/unit/*.test.ts`.

---

### 4. Импорт старого CV: PDF/DOCX → структурный JSON

**У них:** `packages/ai/src/prompts/parser-system.md` — образцовый строгий
промпт: жёсткие ограничения («извлекай только явно указанное, никогда не
додумывай, сохраняй язык оригинала»), явный **порядок разрешения конфликтов**
(валидность схемы → верность источнику → пропустить неуверенное) и контракт
вывода («только один сырой JSON, без markdown»). Плюс
`packages/ai/src/resume/sanitize.ts` для чистки результата.

**У нас:** уже есть весь пайплайн — `lib/classify.ts` с цепочкой провайдеров
(Yandex → GLM → Anthropic), согласие пользователя на ИИ
(`userWantsAi`), `app/api/classify/route.ts`, редакция персональных данных
(`lib/ai/redaction.ts`). Не хватает **одного типа документа**: «резюме».

**Что делать:** добавить ветку «это CV» в классификацию: пользователь
загружает свой старый PDF/DOC — мы заполняем структурный профиль из пункта 1.
Промпт писать по их шаблону (порядок конфликтов + запрет на выдумывание — это
именно то, что защищает нас от галлюцинаций в чужой трудовой истории).

**Зачем:** это самый сильный онбординг-ход для кандидата: он не заполняет
форму, он загружает файл, который у него уже есть.

**Оценка:** ~1 день поверх существующего пайплайна.

---

### 5. Портируемость: JSON Resume

**У них:** `packages/import/src/json-resume.tsx` — импорт открытого стандарта
JSON Resume (и своего формата) с аккуратным разбором частичных дат
(`YYYY`, `YYYY-MM`, `YYYY-MM-DD`).

**Зачем нам:** у нас в маркетинге уже заявлено «экспорт без привязки»
(`lib/segments.ts`). Импорт/экспорт JSON Resume — это дешёвый способ сделать
заявление проверяемым, плюс канал притока пользователей из других сервисов.

**Оценка:** ~0.5 дня в обе стороны, чистая функция + тест.

---

### 6. Трекер откликов на стороне кандидата

**У них:** `packages/schema/src/applications/data.ts` — фиксированный enum
стадий, таймлайн как дискриминированное объединение `stage | note`,
`archived` булевым флагом вместо удаления, поле `aiMetadata` как свободный
`record` под будущее обогащение без миграции.

**У нас:** стадии живут на стороне работодателя; `app/my/applications` — одна
страница списка. Их модель таймлайна («стадия» и «заметка» — одна лента) —
хороший готовый паттерн, если будем делать кандидату историю отклика.

**Оценка:** ~1 день, но это уже продуктовое решение, а не заимствование.

## Что брать не стоит

- **Движок шаблонов и style-rules** (`packages/schema/src/resume/data.ts`,
  секции `styleRules`, `typography`, `layout`, `pages`) — сотни строк ради
  задачи «выбрать шрифт и колонки». Нашей аудитории (няня, водитель, персонал
  виллы, экспат) нужен один аккуратный шаблон, а не двенадцать.
- **Свой шрифтовой пакет** (`packages/fonts` + webfontlist) — вес без пользы.
- **Passkeys/2FA/OAuth-контур** — у нас Supabase Auth и 2FA уже есть.
- **Монорепо на turbo/biome/knip** — миграция ради миграции; наш single-app
  Next.js справляется.
- **MCP-пакет** (34 инструмента) — правильное направление на будущее
  («doki как инструмент для агента: подай отклик, собери документы»), но не
  сейчас: сначала должна появиться структурная модель.

## Юридика и зависимости

- **MIT** — можно копировать код и производные, требуется сохранять текст
  лицензии и копирайт. Для файлов, скопированных дословно, добавляем шапку
  «Adapted from Reactive Resume (MIT), © 2026 Amruth Pillai».
- Их схемы написаны на **zod**, которого у нас в `package.json` нет. Для
  подмножества модели резюме zod не обязателен — можно обойтись типами TS +
  ручной валидацией, как сейчас в `lib/career.ts`. Тянуть zod стоит только если
  решим валидировать импорт из внешних источников (JSON Resume, ответ ИИ) —
  там он оправдан.
- Новые зависимости, которые реально появятся: `@react-pdf/renderer`
  (~1 пакет + шрифты), опционально `docx`. Обе — MIT.

## Предлагаемый порядок

**Волна 1 — фундамент (2–3 дня).**
Структурная модель резюме (п.1) + `lib/resumeQuality.ts` (п.3).
Пока без ИИ и без PDF: сразу видно полноту профиля, работодатель начинает
видеть нормальную карточку кандидата, а не только имя и WhatsApp.

**Волна 2 — выдача (1.5–2 дня).**
PDF-рендер (п.2): CV кандидата → в отклик и в сейф. Тот же рендер сразу
переиспользуем для справки о работе из `employments`.

**Волна 3 — трение к нулю (1.5 дня).**
Импорт старого CV через существующий классификатор (п.4) + JSON Resume (п.5).

**Что делает всё это нашим, а не копией:** каждая строка опыта в резюме может
ссылаться на `employments` и на верификацию работодателя. Резюме на doki.help —
не «что человек о себе написал», а «что подтверждено документами и работодателем
внутри системы». Именно этого Reactive Resume дать не может по своей природе, и
именно это стоит выносить в позиционирование.

## Было → станет (по экранам и сущностям)

Ниже — то же самое, но в виде конкретных изменений. «Было» проверено по коду,
«станет» — предлагаемое состояние после трёх волн.

### 1. Таблица `resumes`

| | |
|---|---|
| **Было** | Одна строка на пользователя: `full_name, headline, location, contact, email, about, experience text, custom_fields jsonb` (`supabase/migrations/20260703140000_resumes.sql`). Весь опыт работы — один текстовый абзац. |
| **Станет** | Плюс `sections jsonb`: `experience[]`, `education[]`, `skills[]`, `languages[]` — каждая запись с `id`, периодом и описанием. Старый `experience text` остаётся и читается как fallback. |
| **Ломается ли** | Нет. Миграция аддитивная, RLS не меняется, старые записи продолжают открываться. |

### 2. `/my/resume`

| | |
|---|---|
| **Было** | Одна плоская форма: 7 полей + «свои поля», кнопка «Сохранить» (`app/my/resume/ResumeForm.tsx`). Никакой обратной связи о качестве и никакого выхода наружу. |
| **Станет** | Редактор секций (добавить место работы: должность, компания, период, обязанности) + полоса полноты профиля с конкретными подсказками («нет WhatsApp», «период задом наперёд») + кнопка «Скачать CV (PDF)» + кнопка «Загрузить старое CV и заполнить автоматически». |

### 3. Отклик `/apply/[slug]`

| | |
|---|---|
| **Было** | Из резюме берутся **только** `full_name`, `contact`, `email` для предзаполнения полей формы (`app/apply/[slug]/page.tsx:150`). Сам опыт работы работодателю не уходит вообще. Кандидат может приложить документы из сейфа и ответить на скрининг-вопросы. |
| **Станет** | К отклику прикладывается структурный опыт и/или сгенерированный CV-однострочник. Кандидат по-прежнему решает, что прикладывать, — согласие и приватность не меняются. |

### 4. Карточка кандидата у работодателя

| | |
|---|---|
| **Было** | Имя, стадия/состояние, WhatsApp, email, ответы на скрининг-вопросы, приложенные документы, ИИ-прогоны (`app/employer/candidates/[applicationId]/page.tsx`). Опыта работы нет ни в каком виде. |
| **Станет** | Плюс блок «Опыт» с пометкой **«подтверждено в doki»** там, где строка связана с `employments` / `employment_verifications`, и кнопка «Скачать CV (PDF)». Это и есть то, что нельзя скопировать у Reactive Resume. |

### 5. `/my/career`

| | |
|---|---|
| **Было** | Таймлайн из `employments`, только чтение (`app/my/career/page.tsx`, `lib/careerTimeline.ts`). Живёт отдельно от резюме. |
| **Станет** | Источник строк резюме: «добавить в резюме» прямо из подтверждённого места работы. Резюме перестаёт быть отдельной самодекларацией. |

### 6. Сейф и обмен

| | |
|---|---|
| **Было** | В сейфе только то, что загрузил пользователь. Обмен — signed URL, TTL, отзыв, лимит просмотров, аудит, share-пакеты (`share_packages`, `revoke_share_package`). |
| **Станет** | Сгенерированный CV кладётся в сейф как **обычный документ** (`documents` + `document_files`) — и автоматически получает весь существующий контур обмена. Ни строчки нового кода в шаринге. |

### 7. Кадровые документы работодателя

| | |
|---|---|
| **Было** | Данные есть — `employments`, `offers`, `employment_verifications`, `final_documents` — а файла на выходе нет. Работодатель не может выдать бумагу из системы. |
| **Станет** | Тот же PDF-рендер выдаёт справку о работе и оффер из уже имеющихся данных. Это побочный, но, возможно, самый монетизируемый эффект всей затеи. |

### 8. Импорт и экспорт

| | |
|---|---|
| **Было** | `/my/export` — JSON-дамп сейфа (`app/my/export/route.ts`: members, documents, records, метаданные файлов). Импорта нет вообще. |
| **Станет** | Плюс импорт старого CV через существующий классификатор и импорт/экспорт JSON Resume. Заявление «экспорт без привязки» (`lib/segments.ts`) становится проверяемым в обе стороны. |

### 9. Проверки качества

| | |
|---|---|
| **Было** | Две детерминированные проверки: качество вакансии (`lib/vacancyQuality.ts`) и комплектность документов отклика (`lib/ai/completeness.ts`). Профиль кандидата не проверяется ничем. |
| **Станет** | Третья проверка того же вида — полнота профиля кандидата (`lib/resumeQuality.ts`). Без LLM, объяснимая, даёт метрику для аналитики воронки. |

### Что не меняется

Auth и 2FA, модель RLS, структура сейфа, контур обмена, стадии на стороне
работодателя, i18n-подход (ru/en/id/uz словарями в компонентах), провайдеры ИИ
(`Yandex → GLM → Anthropic`) и согласие пользователя на распознавание.

### Что увидит пользователь в конце каждой волны

- **Волна 1.** Кандидат заполняет опыт по местам работы и видит полноту профиля;
  работодатель впервые видит в карточке опыт, а не только имя и WhatsApp.
- **Волна 2.** У кандидата появляется кнопка «Скачать CV» и CV в сейфе;
  у работодателя — «Скачать CV кандидата» и справка о работе для сотрудника.
- **Волна 3.** Новый кандидат загружает старый файл CV и получает заполненный
  профиль за один шаг вместо формы.

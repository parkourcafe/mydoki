## 1. Полная карта системы (контекст)

Doki.help — защищённая система для документов, найма и трудовых отношений. Три направления: **для людей**, **для работодателей**, **для семей** (семьи = функция личного vault, не отдельный кабинет до фазы 4).

**Хребет продукта — единая цепочка:**

- Человек: профиль → поиск работы → подача документов → отбор → оффер → оформление → работа → изменения → законное завершение → сохранённая профессиональная история.
- Работодатель: понять, кого искать → вакансия → кандидаты → проверка данных → структурированный отбор → оформление → адаптация → управление документами → корректное завершение.

**Фазы строительства:**

| Фаза | Содержание | Статус |
|---|---|---|
| 0 | Аудит существующего кода | делается первой |
| **1** | **Личный vault + базовый найм (это ТЗ)** | **реализуется сейчас** |
| 2 | Оффер, оформление, Employment (карточка сотрудника ⇄ «Мои трудовые отношения»), онбординг | только учесть в модели данных |
| 3 | Изменения в работе, напоминания работодателя, юридический помощник (RAG, одна юрисдикция) | не реализуется |
| 4 | Увольнение как процесс, архив, внешняя верификация, семейный доступ | не реализуется |

**Ключевая сущность будущего (фаза 2): `Employment`** — одна запись о трудовых отношениях с двумя проекциями: карточка сотрудника в кабинете работодателя и раздел «Мои трудовые отношения» у человека. В фазе 1 таблица не создаётся, но `Application` (отклик) должен иметь терминальный статус `hired`, из которого фаза 2 породит Employment.

**AI-архитектура (все фазы):** десять функциональных ролей (Vacancy Discovery, Vacancy Structuring, Candidate Evidence Extractor, Completeness Checker, Consistency Checker, Interview Planner, Employment Document Assistant, Legal Process Guide, Quality Critic, Human Review Gate) реализуются как **4 сервиса**: Vacancy Assistant, Candidate Analyzer, Process Guide (фаза 3), Guardrails (слой политики, не агент). В фазе 1 — только Vacancy Assistant и Candidate Analyzer + Guardrails.

**Полная карта маршрутов (для контекста; фаза 1 реализует помеченные ✅):**

Публичная часть: `/` ✅ · `/for-people` ✅ · `/for-employers` ✅ · `/security` ✅ · `/pricing` ✅ · `/about` ✅ · `/jobs` (фаза 2+, публичной доски вакансий в фазе 1 нет — вакансии доступны по прямой ссылке `/v/[slug]` ✅) · `/document-vault` ✅ (лендинг) · `/employment` (фаза 2) · `/legal-guides` (фаза 3)

Кабинет человека: `/app/home` ✅ · `/app/documents` ✅ · `/app/profile` ✅ · `/app/jobs` ✅ (мои отклики доступны и здесь) · `/app/applications` ✅ · `/app/reminders` ✅ · `/app/shared` ✅ · `/app/employment` (фаза 2) · `/app/legal-help` (фаза 3)

Кабинет работодателя: `/employer/dashboard` ✅ · `/employer/vacancies` ✅ · `/employer/vacancies/new` ✅ · `/employer/candidates` ✅ · `/employer/settings` ✅ · `/employer/employees` (фаза 2) · `/employer/onboarding` (фаза 2) · `/employer/documents` (фаза 2) · `/employer/templates` (фаза 3) · `/employer/legal` (фаза 3) · `/employer/reports` (фаза 3)

## 2. Границы фазы 1

**Входит:**

1. Аутентификация и два типа аккаунтов: личный и работодательский (человек может состоять в компании, сохраняя личный аккаунт).
2. Личный Doki-профиль (vault): загрузка и хранение документов по категориям, сроки действия, напоминания, защищённая передача по ссылке, пакеты документов, история версий.
3. Работодатель: компания, создание вакансии с AI-ассистентом (Discovery + Structuring), воронка кандидатов, запрос документов у кандидата, карточка кандидата с AI-анализом (факты, пробелы, несоответствия, вопросы — с основаниями).
4. Отклик человека на вакансию по прямой ссылке: выбор пакета документов из vault, ответы на screening questions, отслеживание статуса.
5. Публичные страницы (список выше).
6. Сквозная безопасность: шифрование файлов, аудит-лог доступов, согласия, автоудаление данных отклонённых кандидатов.

**Не входит (не реализовывать):** оффер-генерация; Employment и всё после найма; онбординг; юридический помощник; внешняя верификация (вузы/работодатели); e-signature; публичная доска вакансий; семейный доступ; отчёты; шаблоны. Автоматические проверки документов (срок, совпадение имени, целостность) — входят; вынесение вердикта «подделка» — запрещено, только статусы и несоответствия.

## 3. Стек и принципы

- **Next.js 15+ (App Router, TypeScript strict)** — фронт и API (route handlers / server actions). Если в существующем коде другая структура — зафиксируй в CODE_AUDIT.md и предложи путь миграции, не переписывай молча.
- **PostgreSQL** + ORM (Prisma или Drizzle — что уже используется в репо; если ничего — Drizzle). Все изменения схемы — миграциями.
- **Хранилище файлов: S3-совместимое** (в dev — MinIO). Файлы шифруются на стороне сервера (SSE или envelope encryption с ключами per-user; см. §8). Доступ к файлам — только через подписанные URL с коротким TTL, никогда напрямую.
- **AI:** вызовы LLM через один внутренний модуль `lib/ai/` с провайдер-абстракцией (ключи в env). Все промпты — версионируемые файлы в `lib/ai/prompts/`, не строки в коде.
- **Очередь фоновых задач** (напоминания, анализ документов): pg-boss или BullMQ — по тому, что проще в текущей инфраструктуре.
- **i18n:** русский — первый язык, все строки через словарь (next-intl или аналог), без хардкода текста в компонентах.
- Тесты: unit на бизнес-логику (комплектность, сроки, статусы воронки), integration на API. E2E (Playwright) — на три критических пути: загрузка документа, создание вакансии, отклик.

## 4. Модель данных (фаза 1)

Ниже — логическая схема. Имена смысловые; согласуй с существующими таблицами в фазе 0.

### 4.1. Пользователи и компании

- **users**: id, email (uniq), password_hash / oauth, name, locale, created_at. Один user — всегда человек с личным vault.
- **companies**: id, name, slug, country, created_at.
- **company_members**: user_id, company_id, role (`owner` | `recruiter`), created_at. Членство не отменяет личный аккаунт.

### 4.2. Vault

- **documents**: id, owner_user_id, category (enum: passport, diploma, certificate, resume, recommendation, visa, insurance, employment_contract, medical, family, other), title, issued_at, expires_at (nullable), status (`active` | `archived`), current_version_id, created_at.
- **document_versions**: id, document_id, file_key (S3), file_hash (sha256), mime, size, uploaded_at, note. История изменений = версии; удаление версии запрещено, только архивация документа.
- **document_checks**: id, document_version_id, check_type (`expiry` | `name_match` | `date_consistency` | `file_integrity`), result (`pass` | `mismatch` | `unreadable`), details (jsonb), checked_at. Автоматические проверки; терминов «подделка/фальшивый» нет нигде — ни в коде, ни в UI.
- **reminders**: id, user_id, document_id (nullable), title, due_at, offsets (jsonb, напр. [-30, -7, -1] дней), channel (`email`), status. Генерируются автоматически из expires_at + создаются вручную.
- **share_links**: id, owner_user_id, token (uniq, случайный), scope (список document_id или bundle_id), expires_at, max_views, password_hash (nullable), revoked_at, created_at.
- **share_access_log**: id, share_link_id, accessed_at, ip, user_agent. Владелец видит каждый доступ.
- **bundles** (пакеты документов): id, owner_user_id, title, purpose, created_at; **bundle_items**: bundle_id, document_id, position.

### 4.3. Найм

- **vacancies**: id, company_id, slug (uniq, для `/v/[slug]`), title, status (`draft` | `published` | `closed`), problem_statement, daily_tasks (jsonb), must_have (jsonb), trainable (jsonb), required_documents (jsonb: категории + обязательность), screening_questions (jsonb: [{id, text, type: text|choice|file}]), scorecard (jsonb: критерии), stages (jsonb, дефолт: new → review → interview → assignment → decision), success_criteria_probation, created_by, created_at, published_at.
- **applications**: id, vacancy_id, applicant_user_id, stage (текущий этап из stages), state (`active` | `hired` | `rejected` | `withdrawn`), rejected_reason (nullable), answers (jsonb — ответы на screening questions), created_at, updated_at. Уникальность: (vacancy_id, applicant_user_id).
- **application_documents**: id, application_id, document_id, document_version_id (фиксируем версию на момент подачи), requested_category, status (`provided` | `missing` | `expired`). Комплектность = вычисляется по required_documents вакансии; «документы не заполнены» — это флаг, **не этап воронки**.
- **application_events**: id, application_id, actor (user_id | `system` | `ai`), type (stage_change, note, document_request, ai_analysis, consent, …), payload (jsonb), created_at. Единая лента истории общения и заметок команды.
- **consents**: id, user_id, application_id (nullable), kind (`data_processing`), granted_at, revoked_at, text_version. Отклик невозможен без активного согласия.

### 4.4. AI

- **ai_runs**: id, kind (`vacancy_discovery` | `vacancy_structuring` | `evidence_extraction` | `completeness` | `consistency`), subject_type/subject_id (vacancy | application), prompt_version, model, input_digest, output (jsonb), groundings (jsonb — основание каждого вывода: цитата + источник-документ), created_at, reviewed_by (nullable), review_action (`accepted` | `edited` | `rejected`, nullable). **Human Review Gate = ни один ai_run не влияет на статус кандидата, пока reviewed_by IS NULL.**

### 4.5. Сквозное

- **audit_log**: id, actor_user_id, action, object_type/object_id, ip, created_at. Пишется на каждый просмотр/скачивание документа, каждое изменение стадии, каждый вход по share-ссылке.
- **retention_jobs**: автоудаление данных отклонённых кандидатов через настраиваемый срок компании (дефолт 12 мес.): по истечении — обезличивание application + отзыв доступа компании к документам (сами документы остаются у владельца в vault — они его).

**Задел под фазу 2 (только не заблокировать):** application.state = `hired` — точка, из которой создастся Employment; document_versions неизменяемы; company_members расширяем ролями. Таблицу employments НЕ создавать.

### 5.3. Кабинет работодателя (`/employer/*`)

- **/employer/candidates** — воронка: kanban по этапам вакансии; на карточке — имя, этап, индикатор комплектности, флажки несоответствий. Drag между этапами = stage_change.
- **Карточка кандидата** (`/employer/candidates/[id]`): вкладки «Профиль и резюме», «Документы» (статус каждого требуемого документа; кнопка «запросить недостающие»), «Ответы», «AI-анализ» (§7.2–7.3: подтверждённые факты, несоответствия, пробелы, вопросы к интервью — каждый пункт с основанием-цитатой; кнопки Принять/Редактировать/Отклонить на каждый блок), «История» (application_events + заметки команды), «Согласия». ## 6. API (контракт фазы 1, REST поверх route handlers)

Аутентификация — сессии (cookie) для web. Все ответы — типизированы, ошибки — единый формат `{error: {code, message}}`.

- `POST /api/auth/register | login | logout`
- `GET|POST /api/documents` · `GET|PATCH|DELETE /api/documents/:id` (DELETE = archive) · `POST /api/documents/:id/versions` · `GET /api/documents/:id/checks`
- `GET|POST /api/reminders` · `PATCH|DELETE /api/reminders/:id`
- `GET|POST /api/bundles` · `PATCH /api/bundles/:id`
- `GET|POST /api/share-links` · `POST /api/share-links/:id/revoke` · `GET /api/share/:token` (публичный, с проверкой пароля/лимитов/срока)
- `GET|POST /api/companies` · `POST /api/companies/:id/members`
- `GET|POST /api/vacancies` · `GET|PATCH /api/vacancies/:id` · `POST /api/vacancies/:id/publish` · `GET /api/v/:slug` (публичный)
- `POST /api/vacancies/:id/apply` (создаёт application: согласие + ответы + документы из vault) · `GET /api/applications` (свои) · `POST /api/applications/:id/withdraw`
- `PATCH /api/employer/applications/:id/stage` · `POST /api/employer/applications/:id/request-documents` · `POST /api/employer/applications/:id/reject` · `POST /api/employer/applications/:id/notes`
- `POST /api/ai/vacancy-discovery` (диалоговый) · `POST /api/ai/vacancy-structuring` · `POST /api/ai/analyze-candidate` · `POST /api/ai/runs/:id/review` (accept/edit/reject)

Авторизация: владелец видит только своё; работодатель видит документы кандидата **только** в составе отклика и только категории, запрошенные вакансией; каждый просмотр — в audit_log.

## 7. AI-модули фазы 1

Общее: модуль `lib/ai/` с интерфейсом `runAgent(kind, input) → AiRun`. Температуры низкие, выводы — структурированный JSON по zod-схемам, retry при невалидном JSON.

### 7.1. Vacancy Assistant

**Discovery (диалог):** помогает работодателю понять, кого он ищет. Задаёт по одному вопросу: какую проблему решит сотрудник; ежедневные задачи; что обязательно / чему можно научить; какие документы нужны; что будет успешным испытательным сроком. Выход — структурированный бриф.

**Structuring:** из брифа генерирует черновик вакансии: title, описание (без «литературных произведений» — коротко и конкретно), must_have, trainable, required_documents, screening_questions, scorecard, stages, success_criteria_probation. Черновик всегда редактируется человеком до публикации — публикация без просмотра невозможна.

### 7.2. Candidate Analyzer

Запускается по кнопке или при поступлении отклика (фоново). Три прогона:

- **Evidence Extractor:** извлекает из резюме и документов факты (места работы, периоды, образование, сертификаты) — каждый факт с цитатой-источником (документ + фрагмент).
- **Completeness Checker:** сверяет комплект с required_documents и must_have вакансии → список «недостающее» и «пробелы» (напр., нет подтверждения последнего места работы).
- **Consistency Checker:** ищет противоречия (даты пересекаются, имя в дипломе ≠ имени в паспорте, стаж в резюме ≠ датам договоров) → список несоответствий с указанием обоих источников.

Выход агрегируется в карточке: **подтверждённые факты / несоответствия / пробелы / недостающие документы / вопросы для интервью / возможные риски** — с основанием каждого вывода. **Запрещено:** совокупный балл кандидата, ранжирование кандидатов, рекомендация нанять/отказать, суждения о личности, вердикт «подделка».

### 7.3. Guardrails (слой политики)

- Post-processing каждого вывода: если у пункта нет grounding-цитаты — пункт помечается `unsupported` и не показывается без клика «показать неподтверждённые».
- Лексический фильтр запрещённых формулировок (балл, «рекомендуем отказать», «поддельный» и т.п.) — вывод отклоняется и перегенерируется.
- **Human Review Gate:** AI-вывод не меняет stage/state кандидата. Любое действие — только человеком. В UI AI-блоки всегда помечены «AI-анализ, требует проверки» до ревью.

### 7.4. Логирование

Каждый прогон — строка в ai_runs (prompt_version, model, groundings, review_action). Это требование соответствия (EU AI Act: найм — high-risk), не опция.

## 8. Безопасность и приватность (фаза 1, не откладывается)

1. Файлы — только в приватном bucket, отдача только через подписанные URL (TTL ≤ 5 мин); envelope encryption: DEK per-document, KEK в KMS/env.
2. audit_log на каждый доступ к документу (свой, работодателя, по share-ссылке) — владелец видит журнал.
3. Согласие на обработку — обязательный шаг отклика, версия текста фиксируется; отзыв согласия → компания теряет доступ к документам отклика.
4. Retention: автообезличивание отклонённых откликов по сроку из настроек компании (дефолт 12 мес.).
5. Rate limiting на auth и публичные endpoints; пароли — argon2; сессии — httpOnly.
6. Валидация загрузок: mime-sniffing, лимит размера, антивирус-скан (ClamAV в очереди), EXIF-strip у изображений при передаче по share-ссылке.
7. Персональные данные — не в логах приложения; PII-маскирование в error-трекере.
8. Разделение доступа в коде — центральный модуль `lib/authz/` (политики: owner / company member / share token), запрещены ad-hoc проверки в компонентах.

## 9. Критерии приёмки фазы 1

1. Человек регистрируется, загружает паспорт с expires_at, получает автонапоминание за 30/7/1 день (проверяется тестом с фейковым временем).
2. Человек создаёт пакет «для трудоустройства», делится ссылкой с паролем и сроком 7 дней; получатель открывает; владелец видит доступ в журнале; отзыв ссылки мгновенно закрывает доступ.
3. Работодатель проходит AI-мастер вакансии: диалог Discovery → черновик → правки → публикация; вакансия открывается по /v/[slug] без авторизации.
4. Человек откликается: даёт согласие, прикладывает документы из vault, отвечает на вопросы; отклик виден обеим сторонам; работодатель видит только запрошенные категории документов.
5. Candidate Analyzer выдаёт факты/пробелы/несоответствия, у каждого пункта — источник; кнопки ревью работают; неревьюированный вывод не влияет на воронку.
6. Несоответствие имени в двух документах → в карточке несоответствие со ссылками на оба документа; слова «подделка» нет нигде в UI/коде.
7. Перемещение по воронке пишет application_events; кандидат видит смену этапа; отказ — только с причиной.
8. Прямой URL файла из bucket не открывается; подписанный URL истекает; каждый просмотр — в audit_log.
9. Отзыв согласия кандидатом закрывает компании доступ к его документам.
10. Lighthouse ≥ 90 (perf/a11y) на публичных страницах; мобильная вёрстка кабинетов (загрузка документа с телефона — базовый сценарий).
